# ADR 020: A host-supplied redaction hook for `errorRecording.mode`

**Status:** Proposed — design only, no implementation.

**Found by:** direct follow-up to ADR 019 Part 1 (`docs/adr/019-raw-content-on-spans.md`)
and the error-recording/fingerprint single-writer consolidation that shipped
after it. Both already state the limit this ADR designs around, in their own
words: ADR 019's `'normalized'` section reads *"targeted scrubbing, not
general-purpose redaction — read this before treating it as a PII filter,"*
and the README's "Error recording" section states it more starkly —
`normalizeMessage()` matches eight specific, structured shapes (UUIDs,
emails, URLs, IPv4/IPv6, timestamps, paths, hex runs, quoted ids) and *"does
not recognize sensitive content in general."* Neither gap is fixable by
adding a ninth pattern: an API key in a proprietary, undocumented format, an
internal account id, or a customer's name in ordinary prose are not
structurally distinguishable from ordinary text by any pattern this library
could ship — only the host operating the tool knows what their own data
looks like.

## Context

`normalizeMessage()` (`src/fingerprint/normalize/message.js`) and
`parseAndNormalizeStack()` (`src/fingerprint/normalize/stack.js`) are both
fixed, versioned pipelines this library ships and tests. They're good at
what they were built for — the same eight structured shapes fingerprinting
already trusts for hashing — and, by the README's own admission, that is
where their competence ends. A host who knows their proprietary API key
format is `sk_live_[a-z0-9]{32}`, or that their internal account ids look
like `ACCT-\d{9}`, or that customer names appear in prose their own tool
authors write, has no way to extend `normalizeMessage()`'s coverage today
short of forking this library or accepting the exposure `'none'` mode's
blunt "drop everything" is the only alternative to.

This ADR designs a hook: `errorRecording.redactor`, a host-supplied
function that runs as part of `mode: 'normalized'`'s pipeline. Six
decisions below, each argued before it's picked, per this repo's own ADR
discipline (CONTRIBUTING.md's "ADR discipline" section).

## Decision 1 — Scope: one hook, both message and stack

**Both, through a single function call, not two separate hooks.**

The premise in the prompt driving this design is correct as far as it
goes: a V8 `Error.stack` is generated by the engine, not authored by the
throwing code, and structurally contains only function names and
`file:line` locations — it cannot embed a runtime *value* the way a
message string can. ADR 019 already relied on exactly this distinction to
justify treating message and stack completely differently (pattern-scrub
one, cwd-strip-and-reconstruct the other). By that reasoning alone, a host
redactor's job looks like a message-only concern.

But "cannot embed a runtime value" is not the same claim as "cannot embed
anything host-specific." A stack trace's *file paths* still encode
deployment structure `cwd`-stripping doesn't fully address: a multi-tenant
deployment with per-customer paths beneath its own `cwd`
(`/opt/customers/acme-corp/handler.js`, still relative after stripping)
leaks a customer name into every stack frame from that tenant's calls,
and no built-in pattern this library ships is positioned to know that
`acme-corp` is sensitive here while `node_modules` isn't. This is exactly
the class of thing the Context section's framing already settled — *the
host knows their own data; we don't* — and it applies to path segments as
much as it applies to message prose. Scoping the hook to message only
would mean pre-deciding, on the host's behalf, that this particular case
never matters enough to expose — the same kind of overreach `'none'`
mode's own documentation already warns against in the other direction.

**One function, not two,** because the two fields are frequently reasoned
about together (a redactor matching a customer name in the message will
often want the same match applied to any stack frame that also names it),
and because a single call site is simpler to specify a failure/validation
contract for (Decisions 4 and 5) than two independently-failing hooks
would be. A host who only cares about the message is free to return the
`stack` argument unchanged — the two-argument shape costs a message-only
redactor nothing.

**Concretely, this is one invocation per error event, not one per
field.** `redactor({ message, stack })` is called exactly once whether
the redactor changes both fields, one, or neither — never called once for
`message` and again for `stack`. Worth stating plainly, not just leaving
implicit in the code sketch (Proposed shape, below): a host reasoning
about the hook's cost per thrown error needs the call count, not just the
call shape.

## Decision 2 — Ordering: host redactor runs first

**The host's function runs on raw, uncoerced `err.message`/`err.stack` (via
the same `coerceError()` this library's normalization pipeline already
uses — see Decision 3's code sketch), and its output is what feeds this
library's own `normalizeMessage()`/`parseAndNormalizeStack()`, not the
other way around.**

Two properties decide this, both in the same direction:

1. **Defense in depth, with no offsetting cost.** Running the host's
   function first means our own structured-pattern net is still the last
   thing that touches the content before it reaches a span. If the host's
   redactor is imperfect — misses an email shape their own patterns don't
   cover, say — this library's `normalizeMessage()` still gets a chance to
   catch it. The reverse order has no equivalent backstop: if
   `normalizeMessage()` ran first and the host's redactor ran last, a bug
   in the host's function is the final word on what reaches the span, with
   nothing behind it. Given this library never sees the host's redaction
   logic and can't review it, defaulting to "we still get the last,
   independently-tested pass" is the safer posture.
2. **No placeholder-corruption risk.** Running after this library's own
   scrubbing means the host's function receives text already containing
   `<EMAIL>`, `<UUID>`, `<PATH>`-shaped tokens — structured markers the host
   never asked for and whose exact shape isn't part of any documented
   contract. A host redactor written against "ordinary application text"
   assumptions (its own regexes, its own truncation, its own escaping) has
   no reason to expect or correctly handle those placeholders, and could
   plausibly mangle, duplicate, or strip them depending on what its own
   logic does with bracket-delimited tokens. Running first means the host
   never sees a placeholder at all — there is nothing of ours for their
   code to interact badly with.

A secondary, load-bearing consequence of "first": `normalizeMessage()`
truncates its input to 2048 characters as its very first step
(`MAX_INPUT_LENGTH`, `src/fingerprint/normalize/message.js`), *before*
pattern-scrubbing. If the host's redactor ran after that truncation, any
sensitive content past character 2048 in the original message would never
reach the host's function at all — this library would have silently
decided, on the host's behalf, that content wasn't worth showing them.
Running the host first means they see the full, untruncated original text
and get to decide for themselves; our own truncation then applies
afterward, to their output, the same way it always has.

**Accepted limitation of this ordering:** if the host's output happens to
contain one of `normalizeMessage()`'s nine reserved tokens
(`<UUID>`, `<EMAIL>`, `<URL>`, `<IP>`, `<TS>`, `<PATH>`, `<HEX>`,
`<PORT>`, `<ID>`) — not unlikely, since this library's own README and ADR
019 already state those exact spellings in prose, so a host who read the
docs is more likely, not less, to reach for the same words — it passes
through unlabeled, indistinguishable from a token this library generated
itself. The harm is provenance, not exposure: nothing is less redacted
than before, a reader just can't tell which layer produced a given
placeholder. Accepted rather than fixed — namespacing this library's
tokens to remove the collision would change `normalizeMessage()`'s output
shape for every consumer, not just ones using a redactor, which is a
materially bigger change for a cosmetic, low-probability wrinkle.

## Decision 3 — The hard one: span only, never the fingerprint hash input

**The redactor applies only to what `recordThrownException()`
(`src/instrument.js`) writes to the span. `computeFingerprint()`
(`src/fingerprint/compose.js`) is untouched — its `normalizedMessage`/
`stackSignature` hash inputs are still computed from `normalizeException()`
(`src/fingerprint/normalize/exception.js`) run on the real, unmodified
`err`, exactly as today, whether or not a redactor is configured.**

This is the one place a shortcut answer is tempting and wrong in both
directions, so it's argued fully.

**The case for applying it to both.** Consistency: intuitively, "the span
shows redacted text" and "the fingerprint was computed from the same
redacted text" sound like they should agree — a reader comparing
`exception.message` to `mcp.failure.fingerprint` might reasonably expect
one to have been derived from the other. And a host motivated enough to
write a redactor at all plausibly wants *no trace* of the sensitive
content touching this library's pipeline anywhere, hashed or not.

**Why that's not actually the right test.** `mcp.failure.fingerprint` is
not a content-disclosure channel today, and never has been —
`hashInputs()` (`src/fingerprint/hash.js`) is SHA-256, truncated to 64
bits for collision-avoidance-at-scale, not for security, but pre-image
resistance holds regardless of truncation: nobody can recover
`normalizedMessage` from the 16-hex-character `fingerprint` it feeds. Nor
does `mcp.failure.signature` leak it — that field is
`${errorClass}@${fn}:${line}` (`compose.js`), built from the error class
and the top stack frame's identity, never from message content at all.
`docs/known-gaps.md` entry 10 already drew this exact line when it audited
every raw-content channel this library has: `recordException`/`setStatus`
were flagged as "the largest exposure... the largest of the three isn't in
the custom attribute surface at all," while the fingerprint pipeline was
explicitly cleared — *"the normalized string itself is never emitted as
its own attribute — only hashed into `mcp.failure.fingerprint`."* A host
redactor whose entire purpose is
keeping raw content off the wire has literally nothing to do at the
fingerprint hash input: that content was never going out as plaintext
there in the first place, with or without a redactor.

Given the privacy motivation doesn't apply, the only remaining argument for
touching the fingerprint is aesthetic consistency — and against it stands a
concrete, structural cost: **fingerprint stability against a host's own,
unversioned code.** The entire reason `mcp.failure.fingerprint` exists (ADR
006) is "same underlying bug → same fingerprint, regardless of
high-cardinality noise" — a guarantee this library has built real,
tested machinery around (Agent Thrash Detection's session-scoped grouping;
ADR 009's field-level convergence tracking; an operator's own dashboard or
alert keyed on a specific fingerprint value). That guarantee is already
scoped to "stable across this library's own normalization changes, which
are called out in release notes when they happen" — not to arbitrary
external inputs. A host's redactor is exactly the kind of external input
that guarantee was never meant to cover: it is the host's own code, edited
on the host's own schedule, for the host's own reasons, with zero coupling
to `opentel-mcp`'s version or changelog. If it fed the hash, tuning a regex
in the redactor — fixing a bug, adding a pattern, nothing to do with this
library at all — would silently reshuffle every fingerprint value going
forward, breaking any saved dashboard filter or alert rule keyed on the old
ones, with no signal to the operator that this happened or why. That is a
strictly worse, and strictly more externally visible, failure than the
cosmetic "span text and hash input don't visibly match" the "apply to
both" option was trying to avoid.

**Is this the drift bug the single-writer refactor just closed, reopened?**
No — and it's worth stating why explicitly, since the surface-level shape
looks similar. The single-writer consolidation closed an *accidental*
divergence: two independent code paths re-deriving "the normalized message
for this `err`" that happened to agree for `Error` instances and silently
disagreed for everything else, with no one having decided that should be
true. This decision is a *deliberate, single, documented* exception on top
of that same shared pipeline: `normalizeException()` remains the one
function both consumers call, unmodified; the redactor is inserted as an
extra step *before* that call, on the span-writing path only. The
fingerprint path calls `normalizeException()` on `err` exactly as it does
today; the span path calls it on `redactor(coerceError(err))`'s output
instead. That's an intentional change to one consumer's *input*, argued
here and recorded in one place — not two implementations of the same idea
silently disagreeing.

## Decision 4 — Failure handling: never fall back to raw

**A redactor that throws, returns a non-string `message`, or returns
anything other than a string or `undefined` for `stack`, causes that
event to fall back to `'none'`-equivalent behavior — `span.setStatus({
code: SpanStatusCode.ERROR })`, `error.type` still set and capped, no
`exception` event at all — never to `'full'`-equivalent (raw, unredacted)
content. This never throws out of `recordThrownException()` itself, and it
fires a one-time `diag.warn()` naming the failure mode without echoing any
of the content that triggered it.**

This is a deliberate departure from this library's own general
fail-open convention, and the departure is the point, not an oversight.
Every other fallback in this pipeline — `computeFingerprint()`'s
`buildFallback()`, `recordThrownException()`'s own outer `try {} catch
{}` — treats "something unexpected happened" as "degrade to a known-safe
default and keep going," because the alternative (crashing the host's
tool call over an instrumentation-internal failure) is unacceptable. That
principle still holds here for *availability*: a broken redactor must
never crash the request. But it does not follow that the *safe default*
is "behave as if `mode` were `'full'`." A host who configured a redactor
did so specifically because `'normalized'`'s built-in patterns weren't
enough for their content — silently reverting to fully raw output on any
redactor hiccup means the exact content the host went out of their way to
protect reaches the span anyway, with the host having every reason to
believe it doesn't, because they configured a redactor and saw no error.
That is worse than never having shipped the feature: a silent gap nobody
is looking for is strictly more dangerous than a known, documented one.

The correct safe direction is the *more* redacted one, not the *less*
redacted one — matching this project's own repeated pattern of arguing
explicitly which way is safe to fail and then failing that way
(`docs/known-gaps.md` entry 8's "fail toward under-detection, never
over-detection" for thrash; entry 9's "fail toward over-counting, not
under-counting" for budget guardrails). `'none'`-equivalent output is
that direction here: content is withheld, not fabricated or leaked, and
everything else on the span — status code, capped `error.type`,
`mcp.failure.*` when fingerprinting is on — is completely unaffected,
since none of it depends on the redactor at all (Decision 3).

The warning is one-time (matching `cost/budget.js`'s
`recordUnpriced()` and ADR 019 Part 2's model-rejection warning, both of
which fire once per relevant scope rather than once per call, to avoid
turning a persistently-broken redactor into log spam) and reports *shape*,
never content, for the same reason ADR 019 Part 2 gave for its own
rejection warning: a warning that echoes the very text a redaction hook
exists to keep off telemetry would just relocate the leak from spans to
logs, which routinely get piped into a deployment's own aggregation
pipeline — a second, undocumented channel for the identical problem,
dressed up as a fix. "the errorRecording redactor threw / returned a
non-string message / returned an invalid stack for this call; falling
back to no exception content" is the shape of message this should log —
never a value, a length-only description, or a preview.

## Decision 5 — Can a host make things worse? Yes; cap defensively, don't just trust the contract

**The redactor's returned `message` and `stack` are treated as untrusted
input, the same way `err.message`/`err.stack` themselves already are —
length-capped before they're used, not merely documented as "should be
reasonable."**

Two concrete ways a redactor's output could be worse than what it
replaced:

1. **Unbounded growth.** Nothing stops a buggy redactor from returning a
   message far longer than the input — an accidental duplication, a
   debug artifact concatenated in, or (less innocently) a redaction bug
   that expands rather than shrinks. Decision 2's ordering already
   provides real protection here for free, not by design intent alone:
   `normalizeMessage()` unconditionally truncates its input to 2048
   characters as its first step, *before* pattern-scrubbing, and since
   the redactor's output is exactly what feeds that call (Decision 2),
   an arbitrarily long redactor return value is already capped by
   existing, tested code with no new logic required for the message
   side.
2. **The stack side has no equivalent built-in cap.** `parseAndNormalizeStack()`
   bounds the *number* of frames it keeps (`maxFrames`, default 5), but
   does not bound the *length* of an individual matched frame's function
   name or file path — a pathological single "frame" line with a
   gigantic captured `fn`/`file` substring would pass through at whatever
   length the redactor produced. This is a real, narrow gap distinct from
   the message side's incidental protection, and it should be closed
   explicitly rather than left to chance: apply the same defensive length
   cap (reusing `normalizeMessage()`'s `MAX_INPUT_LENGTH`, 2048
   characters, rather than inventing a second magic number) to the
   redactor's returned `stack` string before handing it to
   `parseAndNormalizeStack()`.

Explicitly **not** proposed: constraining a redactor's output to be no
*longer* than its input. A legitimate redactor can reasonably grow text
(replacing a short raw account id with a longer, descriptive placeholder
like `[REDACTED-ACCOUNT-ID]` is a completely normal thing to want) — the
actual risk is *unbounded* growth, which a fixed cap addresses without
penalizing that normal case.

Because of Decision 3, none of this reaches `hashInputs()` — a
pathological redactor output can bloat one span's `exception.message`
attribute, which is a real but bounded (by the cap above) and contained
concern, not a fingerprint-hash-poisoning one.

**Also explicitly not proposed: detecting a redactor that returns
degenerate-but-valid output** — the same fixed string every time, or an
empty string regardless of input. That output passes every check this ADR
defines (a real string, within the length cap) while being useless for
debugging, but this library has no way to distinguish "a lazy or buggy
redactor" from "a host whose policy deliberately redacts everything to
one fixed marker" — the second is a legitimate instance of the exact
fidelity-versus-exposure tradeoff `'none'` mode already exists to serve,
just reached through a different, host-chosen path. Detecting the
difference would need statefully comparing outputs across calls (its own
memory cost, and its own false-positive risk against a host who
correctly, deliberately collapses many distinct messages to the same
placeholder) to catch a pattern that is at least as often intentional as
accidental. Not this library's problem to solve, and not attempted.

## Decision 6 — Which modes: `'normalized'` only, both to invoke and to matter

**The redactor is consulted if and only if `mode === 'normalized'`. Under
`'full'`, it is accepted in configuration but never called. Under
`'none'`, it is likewise never called — there is no message/stack content
on that path for it to act on in the first place. Configuring a redactor
alongside a `mode` other than `'normalized'` produces a one-time
`diag.warn()` at `instrumentMcpServer()` setup, naming the no-op.**

`'full'`'s entire documented meaning — restated three times already across
this library's history (ADR 019 Part 1's own design, this library's README,
and the single-writer refactor's own explicit constraint the last time
this exact question came up: *"'full' mode behavior stays byte-identical.
Do NOT change it"*) — is "byte-identical to `span.recordException(err)`,
untouched." Invoking a host function on that path, even optionally, breaks
the one property `'full'` exists to guarantee: that it means exactly one
thing, unconditionally, for every deployment that hasn't opted into
anything else. A redactor that silently activated itself under `'full'`
the moment a host configured one would make `'full'` mean "untouched,
unless something else is configured" — precisely the ambiguity this mode
was named to rule out.

`'none'` is excluded for a different, simpler reason: there is nothing to
redact. `recordThrownException()`'s `'none'` branch never builds a message
or stack in the first place (`span.setStatus({ code: ERROR })`, full stop)
— calling a host function whose output would just be discarded is wasted
work with no observable effect, and worse, gives a false impression that
the redactor is "active" in a mode where it structurally cannot matter.

The setup-time warning exists because this is a real, easy-to-hit
misconfiguration trap distinct from the ones this config module already
handles: an operator adding `errorRecording.redactor` without also
changing `mode` away from its `'full'` default (the common case — `mode`
defaults to `'full'`; adding a redactor doesn't imply the operator
remembered to also flip it) would otherwise get *silent* no-op behavior —
the redactor visibly present in their config, never once invoked, no
signal anywhere that it isn't doing anything. This is checked once, at
`resolveErrorRecordingConfig()` / `instrumentMcpServer()` setup time, not
per call — cheap, and consistent with this module's existing philosophy of
failing configuration problems loudly at startup rather than per-request.

`errorClass`/`exception.type` (`err.name`/`err.code`) stays entirely out
of the redactor's scope, in every mode — unchanged from today: length-capped
at `MAX_ERROR_CLASS_LENGTH` (128 characters, `compose.js`), never
pattern-scrubbed or redactor-touched. This isn't an oversight; it's the
same distinction `compose.js`'s own docblock already draws for why
`errorClass` gets a length cap instead of scrubbing — *"a class name isn't
expected to contain structured PII shapes... so pattern-matching would be
reaching for a problem this value doesn't really have."* The redactor
hook exists for free text; `errorClass` isn't free text.

## Timing: a slow redactor has no enforceable bound, and choosing synchronous execution doesn't change that

Every decision above treats "badly-behaved" as a question of *output* —
wrong type, wrong shape, wrong length. None of them address a redactor
that is slow: catastrophic backtracking in a regex, an accidental
synchronous file read, or (least likely, but not impossible in every
runtime) a blocking network call. This runs on every thrown-exception
event under `mode: 'normalized'` — not a one-time cost, a per-error one,
paid on the request path.

**A timeout is not feasible here, and the Constraints section's rejection
of async could easily be misread as having already handled this.** That
rejection argues async isn't *justified* by this ADR's threat model
(no motivating use case needs I/O); it says nothing about the hang risk
inherent in the *chosen* synchronous path, which is not actually the
safer option on this specific axis. JavaScript is single-threaded: nothing
in this library's own code can preempt, interrupt, or time-box a
synchronous function that is already executing on the same thread — there
is no `AbortController`, no `Promise.race`, no cooperative check a
callee's own code hasn't opted into, that reaches into a running
synchronous call from the caller's side. The only mechanisms that
actually bound a synchronous function's execution — running it inside a
`worker_threads` worker with a hard `.terminate()`, or inside a
`vm.Script` constructed with a `timeout` option — both require crossing a
thread or realm boundary, with all the overhead, structured-clone
serialization, and complexity that implies for a function whose input and
output are meant to be simple strings. That machinery is disproportionate
to this ADR's own stated threat model (a host's local pattern-matching
logic, not adversarial or sandboxed code) and would reopen exactly the
"heavyweight machinery for a use case that doesn't need it" objection the
Constraints section already raises against async. Adopting it here would
mean rejecting async for being too heavy while accepting something
heavier to solve a narrower problem.

**The honest position is that this is an accepted, undefended risk of
choosing synchronous execution, not a solved one.** A slow redactor
degrades every tool call's error-path latency for as long as it stays
slow — this library has no mitigation for that today, and this ADR
proposes none, because the mitigations that exist cost more than the risk
they'd close for the threat model actually motivating this feature. This
belongs in the same place `docs/known-gaps.md` reserves for a real,
assessed, deliberately-undefended risk (see entry 9's "do nothing beyond
documenting it" as a considered option, not a default) — documented
plainly here and, once implemented, in the README's "Error recording"
section alongside the redactor's other limits, rather than left for an
operator to discover the hard way.

## Proposed shape (illustrative — not implementation)

```js
/**
 * @typedef {object} ErrorRecordingOptions
 * @property {'full' | 'normalized' | 'none'} [mode='full']
 * @property {(input: { message: string, stack: string | undefined }) =>
 *   { message: string, stack: string | undefined }} [redactor]
 */
```

Call site — `recordThrownException()`'s `'normalized'` branch
(`src/instrument.js`), before today's `normalizeException()` call:

```js
if (errorRecordingConfig.mode === 'normalized') {
  let { message, stack } = coerceError(err); // already-shared coercion

  if (errorRecordingConfig.redactor) {
    try {
      const redacted = errorRecordingConfig.redactor({ message, stack });
      if (typeof redacted?.message !== 'string' ||
          (redacted.stack !== undefined && typeof redacted.stack !== 'string')) {
        throw new Error('redactor returned an invalid shape');
      }
      message = redacted.message.slice(0, MAX_REDACTOR_OUTPUT_LENGTH);
      stack = redacted.stack?.slice(0, MAX_REDACTOR_OUTPUT_LENGTH);
    } catch {
      warnRedactorFailedOnce(); // one-time, shape-only diag.warn()
      span.setStatus({ code: SpanStatusCode.ERROR });
      return; // 'none'-equivalent for this event — see Decision 4
    }
  }

  const { normalizedMessage, frames } = normalizeException({ message, stack }, { cwd: process.cwd() });
  // ...unchanged from today onward
}
```

`computeFingerprint()`'s own call, a few lines later in the same catch
block when fingerprinting is enabled, is untouched — it still calls
`normalizeException(err, ...)` directly on the real `err`, never on
`{ message, stack }` above. This is the concrete form of Decision 3.

`normalizeException()` (`src/fingerprint/normalize/exception.js`) would
need a small signature accommodation to accept either a raw `err` (its
current contract, still used by `computeFingerprint()`) or an
already-coerced `{ message, stack }` pair (the redactor's output) —
noted here as an open implementation detail, not resolved by this ADR,
since it doesn't change any of the six decisions above.

**Execution context, stated explicitly rather than left to be inferred
from the sketch above:** the redactor runs synchronously, inline, inside
the span's still-open lifetime — inside the `async (span) => {...}`
callback `tracer.startActiveSpan()` runs, inside the `catch` block that
precedes `wrapToolCallHandler`'s `finally { span.end(); }`. It always runs
*before* `span.end()`, never after — which is what makes it safe for the
unchanged code following it to keep calling `span.addEvent()`/
`setStatus()` with the redactor's (possibly fallen-back) output; an ended
span would silently drop those. It executes nested inside two layers of
exception safety: `recordThrownException()`'s own top-level `try {} catch
{}` (this function's existing, unconditional "never throw" guarantee) and
the dedicated `try {} catch {}` shown above, scoped to just the redactor
call, which is what actually implements Decision 4's fallback. There is
no deferred, batched, or post-export invocation path — nothing about this
hook runs after the span this event belongs to has already completed.

## Constraints accepted

- The redactor is **synchronous only** — no `Promise`/async support. No
  use case in this ADR's own motivating examples (a proprietary key
  format, an internal id shape, a name-in-prose pattern) needs I/O, and
  every other step in this pipeline (`normalizeMessage()`,
  `parseAndNormalizeStack()`, `computeFingerprint()`, its classifiers) is
  already synchronous by design, for hot-path predictability. Async
  support would add a hang/timeout failure mode this ADR's threat model
  doesn't justify.
- The redactor **never touches `computeFingerprint()`'s hash inputs.**
  `mcp.failure.fingerprint`/`signature`/the hashed `normalizedMessage`/
  `stackSignature` are computed from the real, unmodified `err`,
  identically whether or not a redactor is configured.
- The redactor is **only invoked under `mode: 'normalized'`.** A redactor
  configured alongside `'full'` or `'none'` is accepted but never called,
  with a one-time setup warning.
- **On failure (throw, non-string `message`, or an invalid `stack`), the
  event falls back to `'none'`-equivalent output** — never to raw/`'full'`-
  equivalent content — plus a one-time, content-free `diag.warn()`.
- The redactor's returned `message`/`stack` are **length-capped
  defensively** before use, regardless of what the redactor's contract
  says it should return.
- `errorClass`/`exception.type` (`err.name`/`err.code`) is **out of
  scope**, unaffected by the redactor in every mode.
- **No environment-variable equivalent** — a function cannot be expressed
  as an `OTEL_MCP_*` string; this option is JS-config-only, same as
  `costTracking.extractor`/`thrashDetection`'s classifier-shaped options
  already are.
- **No enforceable timeout on redactor execution.** A slow synchronous
  redactor (catastrophic regex backtracking, an accidental blocking call)
  degrades error-path latency for as long as it stays slow, with no
  code-level mitigation — see "Timing," above. Accepted as a real,
  undefended cost of the synchronous-only choice, not treated as solved
  by rejecting async.

## Alternatives rejected

- **Applying the redactor to `computeFingerprint()`'s hash input too.**
  Rejected in Decision 3 — no privacy benefit (the hash was never a
  plaintext channel) against a real, structural cost (fingerprint
  stability tied to unversioned host code).
- **Running the redactor after this library's own pattern-scrubbing.**
  Rejected in Decision 2 — no defense-in-depth backstop if the redactor is
  imperfect, real risk of corrupting placeholder tokens, and would let
  2048-character pre-truncation hide content from the host before they
  ever see it.
- **Falling back to raw/unredacted content on redactor failure.**
  Rejected in Decision 4 — the literal "worse than not shipping this at
  all" trap: false confidence that redaction is active when it silently
  isn't.
- **Async/`Promise`-returning redactor.** Rejected in the Constraints —
  no motivating use case needs it, and it's inconsistent with every other
  synchronous step in this pipeline.
- **A new top-level `redaction` option, sibling to `errorRecording`.**
  Rejected — the hook is meaningless outside `mode: 'normalized'`
  (Decision 6), so it belongs nested inside the option that already owns
  that mode, not as a disconnected sibling a host would have to remember
  to keep in sync with `errorRecording.mode` by convention alone.
- **Extending the hook to `errorClass`/`exception.type`.** Rejected —
  breaks the existing, already-argued distinction (`compose.js`'s own
  docblock, ADR 019 Part 1) that class identifiers are length-capped, not
  scrubbed, because they aren't free text in the first place.
- **Silently dropping an invalid redactor return value with no warning.**
  Rejected for the same reason ADR 019 Part 2 rejected silently dropping
  a rejected `mcp.tool.model` — a real, "should have worked" input
  vanishing with zero signal is the specific disease `docs/known-gaps.md`
  entry 9 diagnosed once already in this codebase; this would be a third
  recurrence of the same mistake, not a new one.
- **Detecting a redactor that returns the same string every call, or
  always empty.** Rejected in Decision 5 — valid output by every check
  this ADR defines, indistinguishable from a host's deliberate,
  legitimate choice to redact maximally, and only detectable at all via
  stateful cross-call comparison this feature doesn't need and shouldn't
  carry.
- **Bounding a slow redactor with a worker thread or a `vm.Script`
  timeout.** Rejected under "Timing," above — both cross a thread/realm
  boundary for a use case (local pattern matching) that doesn't need one,
  reopening the exact "heavyweight machinery" objection already raised
  against async.

## Versioning: recommend v0.14.0

Current published version is `0.13.0` (the same release `errorRecording.mode`
itself shipped in, per ADR 019 and this package's `CHANGELOG.md`). This
feature is purely additive and default-off — a deployment that never sets
`errorRecording.redactor` observes zero behavior change, the same
non-negotiable property every prior `errorRecording`-adjacent change in
this codebase has preserved. That makes it a **minor** version under this
project's own SemVer discipline (CONTRIBUTING.md's release checklist,
`npm version <patch|minor|major>`), not a major one — nothing about
adding an optional hook breaks an existing consumer's types or runtime
behavior.

Scope comparison against the two most recent precedents: this is
comparably sized to ADR 019 Part 1 alone (a new config field, one new
call-site branch reused across both `tools/call` and `tools/list`, a
length-cap/validation step, a new one-time warning, README documentation
following ADR 019's own "operator-facing consequence, separate from the
ADR" pattern) — larger than ADR 019 Part 2's self-contained model-field
gate, but not larger than Part 1 itself, and with no natural pairing
partner the way Part 1 and Part 2 shared one entry-10 investigation. It
should ship alone, as `v0.14.0`, rather than bundled with unrelated work.

Test coverage this implementation will need, beyond what
`test/instrument.error-recording.test.js`'s existing `'normalized' mode`
describe block already has: ordering (host redactor's output is what gets
pattern-scrubbed, not the reverse), the failure-handling fallback for each
of throw/non-string-message/invalid-stack, the length cap on a
pathologically long redactor return value, the `'full'`/`'none'`
no-op-with-warning behavior, and — the one this ADR is most protective
of — a permanent regression test asserting `mcp.failure.fingerprint`
(and its `normalizedMessage` input) is byte-identical for the same `err`
whether or not a redactor is configured, so Decision 3 cannot silently
erode the way the pre-consolidation span/fingerprint drift did. Not in
this list, deliberately: a test for the "Timing" section above — there is
no timeout behavior to assert on, since none exists to implement: that
section documents an accepted risk, not a feature with test-verifiable
behavior.

## Consequences

- No code changes from this ADR. `src/instrument.js`,
  `src/fingerprint/compose.js`, `src/fingerprint/normalize/exception.js`,
  and `src/error-recording/{config.js,types.d.ts}` are all unchanged
  today.
- Sets up a precisely-specified follow-up: a new `redactor` field on
  `ErrorRecordingConfig` (`src/error-recording/types.d.ts`) and
  `resolveErrorRecordingConfig()` (`src/error-recording/config.js`,
  config-time validation: non-function values degrade to "no redactor,"
  matching this module's existing invalid-input discipline); one new step
  in `recordThrownException()`'s `'normalized'` branch, applying to both
  `wrapToolCallHandler` and `wrapToolsListHandler`'s call sites exactly
  as `mode` itself already does; a one-time failure warning and a
  one-time misconfiguration warning; and a README "Error recording"
  subsection stating the same operator-facing consequences Decisions 3
  and 4 argue here, in plain language, once implemented.
- `docs/known-gaps.md` is not touched by this ADR — this is new-feature
  design, not a gap-closure entry, so there's no existing entry to append
  an update to the way ADR 018/019 both did.
