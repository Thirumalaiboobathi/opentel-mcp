## 2. Phase 1: test reliability

### Root causes
| Test | Root cause | Fix |
| --- | --- | --- |
| core `flush-on-exit` (control SIGTERM, beforeExit, 1000 ms cap) | (a) Dev metrics also print every 5 s from the periodic reader, so a slow start-up under load could put the marker on stderr *before* the shutdown flush under test; (b) fixed 15 s child hang guard shorter than start-up on a saturated machine ("fixture did not exit in time"); (c) cap test timed the exit with `Date.now()` against a 5 s bound | Fixture prints `READY` on stderr too and the parent only inspects stderr after it; hang guard 45 s (guard only); cap bound is `0.8 x` the uncapped 10 s exporter timeout (uncapped can only exit at >= 10 s), measured with `process.hrtime` |
| core thrash benchmark | The 500k-call timed loop ran with `vi.spyOn(record)` installed, retaining every call's arguments; measured throughput was dominated by GC of that garbage (6.9k calls/s loaded vs ~85k unloaded) against an absolute 10k/s floor | Spy moved out of the timed loop to a separate untimed isolation pass; bound is now relative to an in-process calibration loop (`< 30x`; measured 5.8-8.7x unloaded and under 8 busy cores) |
| python `test_exporter_url_gets_otlp_json_...flushed_on_normal_exit` | atexit flush runs in a daemon thread joined for at most `flush_on_exit` cap (2 s). On a loaded machine the export to the in-process sink can take longer, the interpreter exits and the thread dies, so no span arrives. Mechanism confirmed by forcing a 1 ms cap, which reproduces exactly the `IndexError` | Child accepts `FLUSH_TIMEOUT_MS`; the test lifts the cap to 60 s (the cap itself is covered by `test_force_flush_bounds.py`) |
| core `staleness.test.js` "stale (maxAgeMs form)" (found by the load runs) | Test builds `asOf: Date.now() - 240_000` and asserts recorded age `>= 240_000`; the system clock stepped backwards (WSL2 host sync): age 232244 | `Date` (only) frozen per shape describe with `vi.useFakeTimers({ toFake: ['Date'] })` |

The global `testTimeout: 20_000` in `packages/core/vitest.config.js` was reverted.

### Node 20 finding
vitest 5.1.0 declares `engines.node: ^22.12.0 || ^24.0.0 || >=26.0.0`; our `engines` is `>=20` and CI tests Node 20 and 22.
Empirically the core (1311 tests) and ui (230) suites passed on Node 20.20.2 with vitest 5.1.0 (one ui run hit a reporter error once and passed on re-run), but that is
outside vitest's supported range, so tests were moved to **vitest 4.1.12** (`engines: ^20.0.0 || ^22.0.0 || >=24.0.0`, the newest 4.x) for both packages and
`@vitest/coverage-v8`. Engines field unchanged. After the change: core + ui pass on Node 20.20.2 and 22.23.1, coverage threshold OK, typecheck OK,
`npm audit` 0 vulnerabilities, `npm ci --dry-run` OK on npm 10 (Node 20 and 22).
Lockfile note: npm 10.9.8 crashes (`Cannot read properties of null (reading 'edgesOut')`, in peer-set loading) when moving vitest 5 -> 4, so the lock was regenerated with npm 11 after removing the vitest entries; all `@rolldown/binding-*`, `lightningcss-*` and `fsevents` platform entries are preserved (checked), the lock lost only the `esbuild`/`rollup` platform entries that belonged to vitest 5's peer tree.

### Deviations from the brief
- **ADR 030, `maxScanBytes` unit:** the budget is JavaScript string length (UTF-16 code units), not UTF-8 bytes, so a large
  result never needs an encoding pass. The name follows the brief; the unit is documented in the ADR, the d.ts and the README.
- **ADR 029, `added`/`removed`:** evaluated only on complete (unpaginated) listings; events are edge-triggered (once per distinct
  new state) rather than on every `tools/list`; a pinned tool that never appears produces no event. All documented.
- **ADR 029, event emission:** events are added to the `tools/list` span the wrapper holds rather than `getActiveSpan()`, so they
  appear where the host registered no context manager (the existing drift event does not have that property).
- **ADR 031:** the counter depends on fingerprinting (the category is never computed with `fingerprinting:false`), documented
  rather than worked around.
- **ADR 033, demo:** the brief asked for a fake AWS-style key "built at runtime". The fixture holds no key in any form (the leak is
  only its derived attributes), which is stronger; tests that need a key-shaped string assemble it at runtime.
- **ADR 033, UI carries `tools/list` spans:** needed because integrity events live there; admitted only with a whitelisted event.

## 4. Decisions I made

- Reverted the committed `testTimeout: 20_000` (the global raise) and added per-test timeouts only where legitimately slow (listed above).
- Moved vitest 5 -> 4.1.12 (supported on Node 20) rather than changing `engines`. npm 10.9.8 crashes resolving that change, so the
  lockfile was regenerated with npm 11 after removing the vitest entries. Verified: all `@rolldown/binding-*`, `lightningcss-*`,
  `fsevents` platform entries kept; `npm ci` works in a fresh clone on Node 22 (npm 10.9) and `npm ci --dry-run` on Node 20; 0 audit findings.
- One lock side effect: `esbuild`/`rollup` platform entries that belonged to vitest 5's peer tree are gone (nothing in the tree needs them).
- Fixed a third flaky test the load runs exposed (staleness clock-step assertion) with a Date-only fake clock instead of widening a bound.
- Python: changed `CONTRACT_VERSION` from `core 0.17.0` to `core 0.18.0` (and two docstrings). It is a string recording which core
  contract the port conforms to, `contract.json` embeds the core version, and the Python suite asserts they are equal. No behavior change;
  Python 0.1.0 stays unreleased as a new version.
- Used the full 64-hex SHA-256 for integrity hashes (not the 16-hex drift hash) and a hand-written canonicalizer that builds text, because
  copying into a new object would silently drop a `__proto__` key from the hash.
- Count semantics: `secret_leak.count` and the `mcp.tool.secret_leaks` counter: count is a capped magnitude of matches, the counter is +1 per result.
- Windows: new tests were written to be platform-neutral (no POSIX-only calls outside the existing skip pattern) but were only run on Linux here.
- The README examples were verified by extracting the code blocks from the README and running them against the packed tarballs (see 7).
- At the start of the session the security-posture work had not reached `main`, so I stopped; it merged afterwards (b0542ab), so the
  STOP condition no longer applied and I branched from `main` at that point.

## 6. What the tags will trigger

Read from `.github/workflows/release.yml` and `.github/scripts/npm-meta.sh` (unchanged on this branch: `git diff main -- .github` is empty).

`git push origin core-v0.18.0`:
1. `plan`: tag `core-v*` -> core=true. No checkout, no secrets.
2. `build-core` (no publish credentials, Node 22.14.0): `npm-meta.sh` checks the tag equals `core-v` + `packages/core/package.json` version (0.18.0, so it passes) and asks the registry for `opentel-mcp@0.18.0` (404 -> publish=true; 200 -> notice and skip). Then `npm ci`; `npm run test`, `typecheck`, `build` for core (full suite, 1534 tests); `verify:tarball`; `npm pack` into `out/`; CycloneDX SBOM from the packed tarball; uploads artifact `dist-core`.
3. `publish-core` (environment `release`, so it waits for your approval; `id-token: write`): downloads the exact tarball, installs npm 11.21.2 (exists on the registry; trusted publishing needs >= 11.5.1), `npm publish ... --access public --provenance` through OIDC, then `actions/attest` with the SBOM.
4. `publish-ui`/`build-ui` are skipped (ui=false); `github-release` runs because core published: creates release `core-v0.18.0` on the pushed commit and uploads the tarball and `opentel-mcp.cdx.json`.

Then `git push origin ui-v0.4.0`: same shape with `build-ui` (ui tests 263, typecheck, `vite build`, `verify:tarball`, SBOM), `publish-ui` after approval (`publish-core` is skipped, which the `if:` accepts), release `ui-v0.4.0`. Push core first and wait: the concurrency group `release` serializes runs anyway, and ui's peer range already accepts core 0.18.0.

Risks (none found in the workflow itself; these are setup/ordering):
- **Trusted publishers must exist on npmjs.com for both packages** (owner `Thirumalaiboobathi`, repo `opentel-mcp`, workflow `release.yml`, environment `release`). npm does not validate on save; a mistake appears as `ENEEDAUTH` at the publish step, after tests have passed. This is the first release through the pipeline, so nothing here has been exercised against the real registry. The `release` environment and tag rules must also exist (see `docs/security/releasing.md`).
- `gh attestation verify` of the SBOM predicate has not been checked against a real release (as `releasing.md` already says).
- Re-running is safe: an already-published version is skipped.
- The workflow was not changed, so actionlint was not re-run.
