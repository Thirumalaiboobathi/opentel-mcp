- `packages/ui/test/e2e-silent-failure.test.js` plus fixture
  `packages/ui/test/fixtures/e2e-instrumented-server.mjs`.
- **Pipeline under test, with nothing mocked:**
  1. The SDK `Client` connects over **stdio** (`StdioClientTransport`) to a
     child-process `McpServer`, instrumented by core with
     `setupNodeSdk: true, exporterUrl`.
  2. Core exports over **OTLP/HTTP JSON** to the real CLI server

  `OTEL_BSP_SCHEDULE_DELAY=100` only speeds up export; correctness doesn't
  depend on it. `client.close()` terminates the child, and I confirmed no
  child process is left behind. Paths come from `fileURLToPath` and the child

## 3. Decisions I made

1. **Where the E2E test lives:** in `packages/ui`, which already has
   `opentel-mcp` and `@modelcontextprotocol/sdk` as devDependencies. No core
   changes, and no new dependency of any kind in this run.
2. **How the E2E test starts the UI:** in-process through the real CLI entry
   (`bin/opentel-mcp-ui.js` `main()`) rather than spawning the bin. With
   `--port=0` the CLI logs the requested port (`http://localhost:0`), not the
   bound one, so a spawned bin's port can't be read back reliably. See
   follow-ups.
3. **How the E2E test asserts tool name and classification:** through
   `/api/spans/history`, because `/api/summary` only carries counts. Both
   endpoints are asserted.
4. **Classification asserted** as `failureCategory: 'timeout'` +
   `failureChannel: 'execution'`. The fixture's error text was chosen to hit
   core's timeout classifier deterministically.
5. **The connect screen shows no env-var form.** Core doesn't read an env var
   for `exporterUrl` (the UI README says so), so showing one would be
   inventing API.
6. **The connect screen's endpoint comes from `window.location.origin`**, the
   address the browser actually reached, rather than a server-provided value.
   That's correct for any port, including ports other than 4319.
7. **No connect screen before `/api/meta` loads.** The existing `EmptyState`
   covers that moment and the empty-demo edge case.
8. **The connect screen got a Copy button.** Clipboard failures are swallowed
   and the snippet stays selectable.
9. **CHANGELOG entries** go under a new `## Unreleased` heading in
   `packages/ui/CHANGELOG.md`, for the release step to rename to 0.2.0.
10. **Demo duplicate removed at the source:** `computeCompleteness()` returns
    `null` in demo mode (a return-type change), rather than being hidden by a
    component condition.
11. **Health-grade design choices:**
    - worst-of-four rather than a weighted score, for explainability;
    - the thresholds in the table above, and 10 calls as the minimum;
    - nearest-rank p95;
    - no amber for grade C, because the theme reserves amber for "can't tell"
      (`theme/tokens.css` comment).
12. **Demo fixture:** added a sixth tool, `list_calendars`, to show "Not
    enough data". The 42 / 7 / 11 totals are unchanged.
13. **Tool health panel placement:** after the observation matrix, before the
    feed.
14. **ADR numbers:** 024, 025, 026 (the next free numbers after 023).
15. **This report has its own commit,** so it can be dropped without touching
    the task commits.
16. **No visual check.** This environment has no browser, so the connect

    successful build.

## 4. Proposed ADRs

**`docs/adr/024-flush-on-exit.md`: flushOnExit**
- **Findings:** the SDK's stdio client stops a server with stdin EOF → SIGTERM
  at +2 s → SIGKILL at +4 s (`sdk/dist/esm/client/stdio.js:143-176`).
  `beforeExit` only covers the drain-after-EOF path. OTel's own `register`
  entry adds a SIGTERM listener that never exits, which is the hang to avoid.
- **Proposal:** an option `flushOnExit` (`true | { timeoutMs }`) that applies
  only under `setupNodeSdk: true` and does nothing (with a warning) under
  `false`. One process-wide listener set covers `beforeExit`, SIGTERM and
  SIGINT, with re-raise when no host listener exists. Flush is bounded at
  1000 ms (under the SDK's 2 s windows). `shutdown()` is memoized so it never
  runs twice.
- **Recommendation:** the option over a helper; default **on** under
  `setupNodeSdk: true`.

**`docs/adr/025-unactionable-errors.md`: unactionable tool errors**
- **Findings:** content is only seen in the `isError` branch. Every existing
  derivation reads `content[0].text` only. An empty failure already
  fingerprints as category `unknown` with a stable hash.
- **Proposal:** span-only `mcp.failure.unactionable` (boolean) plus
  `mcp.failure.content_length_bucket` (5-value enum), computed from the
  trimmed lengths of text items and the count of non-text items only.
  Unactionable means empty, or under `minTextLength` (default 10) with no
  non-text content. Configured with
  `unactionableErrors: { enabled, minTextLength }`, independent of
  fingerprinting.
- **Recommendation:** span-only for now. Both attributes would be metric-safe,
  but no metric label is proposed, so ADR 021's allowlist and test stay
  unchanged. Fingerprints and categories are untouched. The privacy test uses
  canary strings checked against all exported spans and metrics.

**`docs/adr/026-resources-prompts-coverage.md`: resources/\* and prompts/\***
- **Findings:** ADR 010's default-on `tools/list` wrapping made upgrades throw
  for low-level `Server` users. v2 `McpServer` registers resource/prompt
  handlers **in its constructor** when capabilities are declared, so strict
  instrument-first is impossible there.
- **Proposal:** detect-and-skip per method with a `diag.warn`, never throw;
  opt-in `coverage: { resources, prompts }` in 0.16. Span names are the method
  names, plus `prompts/get {name}`. `gen_ai.tool.name` is absent, and URIs and
  prompt arguments are never captured. A new duration histogram is labeled
  only by `mcp.method.name`, which grows from 2 to 7 fixed values with no new
  label keys. Fingerprinting and channel apply to thrown errors; thrash, cost
  and silent-failure don't.
- **Recommendation:** opt-in now, default-on later. The UI must stop counting
  non-`tools/call` spans in its matrix first.

## 6. Follow-ups noticed but not done

1. **Pre-existing core bug: v2 `McpServer` with `capabilities: { tools: {} }`
   makes `instrumentMcpServer()` throw `INSTRUMENT_FIRST_ERROR`, whatever the
   call order.** The v2 constructor registers tool handlers eagerly
   (`@modelcontextprotocol/server` 2.3.1 `mcp-DIH4cS6P.mjs:1695`; identical in
   2.0.0). I verified this empirically. No test covers it. Not fixed: this run
   allowed no core runtime changes. Raised in ADR 026, Open question 2.
2. **The CLI logs the wrong port with `--port=0`:** it prints
   `http://localhost:0` (`bin/opentel-mcp-ui.js` logs the requested `port`,
   not `server.address().port`).
3. **`opentel-mcp-ui` counts every buffered span** in `/api/summary`,
   regardless of method (`src/summary.js:31-37`). That's harmless today and a
   prerequisite fix before ADR 026 ships.
4. No test keeps `docs/health-grades.md` in sync with `THRESHOLDS` in
   `healthGrades.ts`.
5. The ui README's demo section doesn't mention the new Tool health panel.
6. The E2E test and the Windows `verify-tarball` job haven't run on
   macOS/Windows yet; CI will be their first run.
7. The core README quickstart and the examples still carry the `beforeExit`
   block, pending ADR 024 approval.
8. Still open from Phase 0: `npm audit` findings in the dev/example tree, and
