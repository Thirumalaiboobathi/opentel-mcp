## 2. Task 1: deprecated OpenTelemetry packages

**Replaced.** `@opentelemetry/sdk-trace-node` and `-base` (deprecated: "Use @opentelemetry/sdk-trace package") by
`@opentelemetry/sdk-trace` `^2.9.0`. Checked on npm: sdk-trace has 2.9 to 2.12 and 3.x. 3.x needs Node >= 22.15 and
`@opentelemetry/api` >= 1.10, which breaks core's `engines` (>=20) and the rest of the 2.x tree, so 2.x it is.

| Old | New |
|---|---|
| `NodeTracerProvider` + `provider.register()` | `TracerProvider` (no `register()`), then explicit `trace.setGlobalTracerProvider`, `AsyncLocalStorageContextManager` (enabled and set globally) and the W3C trace-context + baggage `CompositePropagator` |
| `new SimpleSpanProcessor(exporter)` | `new SimpleSpanProcessor({ exporter })` (the new constructors take an options object; this was a real break that the suite caught) |
| `new BatchSpanProcessor(exporter)` | `new BatchSpanProcessor({ exporter, ...OTEL_BSP_* from env })` |

Core runtime deps: removed `sdk-trace-node`; added `sdk-trace`, `context-async-hooks` (moved from dev) and `core`
(promoted from transitive). No new package enters the install tree (24 packages installed for core + ui together).
UI runtime deps are still none; its dev deps swapped to `sdk-trace`. `index.d.ts` only had doc-comment mentions of
`NodeTracerProvider`, which I reworded. The peer `@opentelemetry/api: ^1.9.0` is unchanged (see Decisions).

**Behavior differences checked**
- Same: async context propagation (verified with a runtime script: active span survives an `await` inside
  `context.with`, and `inject` emits `traceparent`), stderr exporter, OTLP export, `flushOnExit`, single shutdown
  (the two "no double shutdown" tests pass). Default sampler is parent-based always-on in both.
- **Different, and fixed:** the old base `BatchSpanProcessor` read `OTEL_BSP_*` env vars; the new one doesn't. I
  re-implemented the four (`MAX_QUEUE_SIZE`, `MAX_EXPORT_BATCH_SIZE`, `SCHEDULE_DELAY`, `EXPORT_TIMEOUT`) with a new
  test, `instrument.batch-env.test.js`, which fails without the fix and passes with it. The repo's own ui e2e uses
  `OTEL_BSP_SCHEDULE_DELAY`.
- **Different, NOT fixed (documented in the core CHANGELOG):** the new provider no longer reads `OTEL_TRACES_SAMPLER*`
  or `OTEL_SPAN_*_LIMIT`. Only hosts that set those variables and use `setupNodeSdk: true` are affected.
- Test changes: a test-only helper `packages/core/test/helpers/tracer-provider.js` keeps the `register()` ergonomics
  for ~30 test files. ui tests use `trace.setGlobalTracerProvider`.

**Other deprecated deps.** None. The packed core + ui install prints nothing deprecated.
`scripts/verify-no-deprecations.mjs` (new) packs both, installs them into an empty temp project and fails on any
"deprecated" line. Output (the control run is 0.18.0 from the registry, to show the check can fail):


## 3. Task 2: resource/prompt spans in the live dashboard

**Bug confirmed.** `packages/ui/test/e2e-resources-prompts.test.js` (new) drives a real coverage-enabled
`McpServer` and asserts through the UI's HTTP API. Run against the unfixed code, both tests failed with only the
tool call arriving:

```
× OTLP path: stdio server with coverage -> real CLI UI -> /api/spans/history
  Error: timed out waiting for all five resource/prompt methods to reach the dashboard;
  last value: {"spans":[{"name":"tools/call ping", ... }],"size":1}
× in-process path: withUI()'s collector as a real SpanProcessor
  AssertionError: expected [] to deeply equal [ 'prompts/get', 'prompts/list', ...(3) ]
```

The OTLP test spawns a stdio child server (fixture `e2e-coverage-server.mjs`) into the real CLI server. The
in-process test uses `withUI()`'s `CollectorSpanProcessor` as a real span processor on an in-memory-transport
server. Both pass after the fix.

**Fix.** `span-method.js` gains `OPERATION_METHODS` and `isOperationSpanName()` (exact method, or method + space,
so `prompts/get greet` matches but `resources/readx` doesn't). `CollectorSpanProcessor.onEnd()` and
`parseOtlpJsonTraceRequest()` admit those, passed through `toOperationSpan()`, which keeps only id, traceId,
name, timing, status, `error.type` and the `mcp.method.name` / `gen_ai.prompt.name` attributes. No events, no
other attributes. Unit tests in `operation-spans.test.js` include a canary URI, prompt argument and a smuggled
`gen_ai.tool.name`, which are all dropped.

**Still counts only `tools/call`:** hero stat, matrix, `/api/summary` buffered counts, health grades and the
silent-failure feed. These filter by `isToolCallSpan` (unchanged). Both e2e tests assert `summary.buffered` is
exactly `{total:1, success:1, error:0, silentFailure:0}` with 7 resource/prompt spans in the buffer, and that the
canary strings never appear in `/api/spans/history`, `/api/summary` or `/api/meta`. `tools/list` is still admitted
only with a security event. Request size limits and the request guard (`request-guard.js`, `server.js`) are untouched.

## 4. Decisions I made

- **sdk-trace 2.x, not 3.x** (engines/api-peer constraints above).
- **Added `@opentelemetry/core` and `context-async-hooks` as direct runtime deps** rather than reimplementing a
  propagator and context manager; both were already installed transitively, so install size is unchanged.
- **Restored `OTEL_BSP_*` support, did not restore `OTEL_TRACES_SAMPLER*` / `OTEL_SPAN_*`.** BSP tuning is used by
  this repo's own tests; the others were undocumented here and would need a sampler factory. Flagged in the CHANGELOG.
- **Did not tighten the `@opentelemetry/api` peer range.** Core says `^1.9.0`, which admits api 1.10.0 (published),
  while every sdk-trace 2.x (and the old base) peers `<1.10.0`. That mismatch already existed; changing a peer range
  is a user-visible install change, so I left it. Suggest `>=1.9.0 <1.10.0` in a later release.
- **Operation spans share the 1000-span ring buffer** with tool calls (opt-in feature, so acceptable); noted in the
  ui CHANGELOG.
- **Operation spans are narrowed to an allowlist** instead of passing through the attribute bag, so the dashboard
  can't store a URI or argument even from a non-core sender.
- **Contract version.** `conformance/contract.json` is stamped with core's version, so the patch bump forced
  regenerating it and updating `CONTRACT_VERSION` plus two strings in `packages/python` (src + tests) from
  `core 0.18.0` to `core 0.18.1`. Python's own version and release are untouched; its suite is green (718 passed).
  Alternative: decouple the contract label from the core version (not done).
- **`npm pkg fix` changed one thing in ui**: `bin` path `./bin/...` to `bin/...`. Kept. It also changed one line in
  core's `package.json`, restoring an em dash that my own JSON rewrite in Task 1 had escaped (`—`). That
  restore sits in the Task 3 commit; net diff vs main for that line is zero.
- **Corrected a false claim:** core CHANGELOG 0.18.0 said it was "the first release made by the signed release
  workflow". It was manual. Reworded. Also fixed CONTRIBUTING.md (it said there is no tag-triggered publish
  workflow) and the threat-model dependency count ("four" to "six" `@opentelemetry/*` packages).
- Not touched: the Python section of CONTRIBUTING.md still says "no CI publishing" (stale, but Python is out of scope).
- The workflow was not changed, so actionlint/zizmor were not re-run.

## 5. What the tags will trigger

`core-v0.18.1` (push of tag, `release.yml`):
1. `plan`: sets `core=true`. No checkout.
2. `build-core` (Node 22.14.0, no publish credentials): `npm-meta.sh` checks the tag equals `core-v` + the version
   in `packages/core/package.json` (0.18.1), then GETs `registry.npmjs.org/opentel-mcp/0.18.1`: 404 means publish,
   200 means skip. Then `npm ci`, core tests + typecheck + build, `verify:tarball`, `npm pack`, CycloneDX SBOM,
   upload artifact `dist-core`.
3. `publish-core` (environment `release`, so it waits for your approval; `id-token: write`): downloads the artifact,
   installs npm 11.21.2 (exists on npm; trusted publishing needs >= 11.5.1), runs
   `npm publish out/opentel-mcp-*.tgz --access public --provenance`, then `actions/attest` with the SBOM.
4. `github-release`: creates GitHub release `core-v0.18.1` with the tarball and SBOM.

`ui-v0.4.1`: the same shape with `build-ui` and `publish-ui`. `build-ui` needs only `plan`, not `publish-core`.
`publish-ui` has `needs: [..., publish-core]` but accepts `skipped`, which is what happens in a ui-only run. It also
works if core's run is still pending, because `verify:tarball` resolves the peer `opentel-mcp >=0.8.0 <1.0.0` from
the registry (0.18.0 or 0.18.1 both satisfy it). The ui peer range accepts 0.18.1.

**First-run risks (the workflow has never completed a real publish):**
1. **npm trusted publisher must be registered for both packages** (owner, repo, workflow file `release.yml`,
   environment `release`) at npmjs.com, Settings. If it isn't, `npm publish` fails with an auth/404 error.
   Nothing in the repo can check this.
2. **Environment `release` branch/tag rules.** If its "deployment branches and tags" restriction allows only
   `main`, runs from a `core-v*` tag will be blocked. It must allow those tags (or no restriction).
3. **Tag target.** For tag pushes, nothing checks that the tagged commit is on `main`; tag the merge commit only.
4. **Provenance needs a public repo** and `repository.url` matching it. Both package.json files do
   (`git+https://github.com/Thirumalaiboobathi/opentel-mcp.git`); the repo must be public.
5. **Global npm upgrade** on the runner (`npm install -g npm@11.21.2`) is untested in this workflow.
6. **Attestation step runs after publish.** If `actions/attest` fails (permissions, `artifact-metadata: write`),
   the package is already on npm but `github-release` may not run. Re-running a tag run skips publish (the
   version check returns 200) and won't recreate that state, so you'd need to create the release by hand.
7. **A failed `npm publish` after a partial upload** isn't retried automatically; the version-exists check makes
   a re-run safe.
