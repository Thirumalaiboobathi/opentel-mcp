# Releasing opentel-mcp

How releases are built, signed and verified, and the one-time setup the maintainer must do for the workflow
([`.github/workflows/release.yml`](../../.github/workflows/release.yml)) to work. Requirements below were checked
against the official docs on 2026-11-07; the workflow header lists the sources. Re-check them before changing
versions, since trusted-publishing requirements change over time.

## How a release works

| Step | Where | Credentials |
| --- | --- | --- |
| Resolve targets, check the tag matches the package version, check the registry for that exact version | `plan`, `build-*` jobs | none (`contents: read`) |
| `npm ci`, full tests, typecheck, build, `verify:tarball`, pack, SBOM (or `uv sync --locked`, ruff, mypy, pytest, `uv build`, `twine check`, SBOM) | `build-*` jobs | none |
| Publish the **exact tarball / wheel the build job tested** (downloaded as an artifact), then attest it | `publish-*` jobs, `environment: release` | `id-token: write` (OIDC) only; no long-lived token anywhere |
| Create the tag and GitHub release, attach tarball/wheel + CycloneDX SBOM | `github-release` job | `contents: write` (only this job) |

- A version that is already on the registry is **skipped** with a notice (`already published ... skipping publish`);
  re-running a release is safe.
- `core` is published before `ui` when both are in one run (`publish-ui` needs `publish-core`).
- One workflow file is used for all three packages because npm and PyPI each register a single workflow filename
  per package as the trusted publisher, and `workflow_dispatch: all` needs to order core before ui.
- Provenance is generated by npm automatically for trusted publishing from a public repo (`--provenance` is also passed
  explicitly). PyPI attestations (PEP 740) are on by default with Trusted Publishing; the workflow also sets
  `attestations: true`.
- **Tags:** `core-vX.Y.Z`, `ui-vX.Y.Z`, `python-vX.Y.Z`. The tag must be the prefix plus the version in
  `package.json` / `pyproject.toml` (for example `core-v` + `0.17.1`), otherwise the build fails. The old `v0.17.0` tag (npm `opentel-mcp` 0.17.0) and
  `python-v0.1.0` remain as history; `v*` tags no longer trigger anything.
- **Which versions have provenance:** only releases published through this workflow, starting with `opentel-mcp`
  0.18.1 and `opentel-mcp-ui` 0.4.1. `opentel-mcp` 0.17.0 and 0.18.0, `opentel-mcp-ui` 0.3.0 and 0.4.0, and PyPI
  `opentel-mcp` 0.1.0 were published manually and are **not signed or attested**: they have no npm provenance, no
  PEP 740 attestation, no GitHub attestation and no attached SBOM.

## One-time setup

Do these once, in order. None of this can be done from the repository.

### 1. GitHub

1. **Environment.** Settings → Environments → New environment → `release`. Enable **Required reviewers** (add
   yourself; leave "Prevent self-review" off while you are the only maintainer, or you could not approve your own run) and restrict **Deployment branches and tags** to
   `main` plus the tag patterns `core-v*`, `ui-v*`, `python-v*`.
2. **Tag protection.** Settings → Rules → Rulesets → New tag ruleset: target tags matching `core-v*`, `ui-v*`,
   `python-v*`; restrict creations/updates/deletions to maintainers (and block deletion and force-updates).
3. **Branch protection** for `main` (ruleset): require pull requests and the CI checks (`test`, `verify-tarball`,
   `dependency-audit`, `python`, `conformance`), block force pushes.
4. **Security features.** Settings → Code security: enable *Private vulnerability reporting*, *Dependency graph*,
   *Dependabot alerts* and *Dependabot security updates*; enable *Code scanning* (the CodeQL and Scorecard workflows
   upload results; the first runs happen after the workflow files are on `main`).
5. Settings → Actions → General: set *Workflow permissions* to "Read repository contents" and keep "Allow GitHub
   Actions to create and approve pull requests" off. Optionally require actions to be pinned to a full SHA.

### 2. npmjs.com (repeat for `opentel-mcp` and `opentel-mcp-ui`)

Package → Settings → **Trusted Publisher** → GitHub Actions:

| Field | Value |
| --- | --- |
| Organization or user | `Thirumalaiboobathi` |
| Repository | `opentel-mcp` |
| Workflow filename | `release.yml` (filename only, case-sensitive) |
| Environment name | `release` |

Notes from the npm docs: npm does **not** validate the configuration when you save it; mistakes show up at publish time
as `ENEEDAUTH`. `package.json` `repository.url` must exactly match the GitHub repository (it does in both packages).
A trusted publisher can't be edited, only deleted and recreated. Only GitHub-hosted runners are supported.

**Follow-up (recommended) once a trusted-publishing release has succeeded for a package:** Package → Settings →
Publishing access → *Require two-factor authentication and disallow tokens*. Trusted publishing keeps working (it uses
OIDC); classic/granular tokens stop being able to publish. Then revoke any old automation tokens under Access Tokens.
Do not do this before the first successful OIDC publish, or your manual fallback below needs a 2FA publish.

Confirm 2FA is enabled on the npm account (Account → Two-Factor Authentication, "Authorization and publishing").

### 3. pypi.org

A pending publisher is not needed because `opentel-mcp` already exists on PyPI. Project → Manage → Publishing →
Add a GitHub publisher:

| Field | Value |
| --- | --- |
| Owner | `Thirumalaiboobathi` |
| Repository name | `opentel-mcp` |
| Workflow name | `release.yml` |
| Environment name | `release` |

Then remove any API tokens for the project (Account settings → API tokens) after the first successful trusted release.
Confirm 2FA is enabled on the PyPI account (PyPI requires it for publishers). No TestPyPI path is included (see the
run report, "Decisions I made"); if you want a dry-run target later, add a separate workflow file and a separate
trusted publisher on test.pypi.org rather than reusing `release.yml`.

### 4. GitHub account

Confirm 2FA (preferably a security key / passkey) is enabled on the GitHub account that owns the repository.

## Cutting a release

1. Bump the version in `packages/<core|ui>/package.json` (or `packages/python/pyproject.toml`), update the package
   `CHANGELOG.md`, merge to `main` through a PR with green CI.
2. Either
   - push the tag on the merge commit: `git tag core-v0.17.1 && git push origin core-v0.17.1` (`ui-v...`,
     `python-v...` likewise), or
   - Actions → Release → *Run workflow* on `main`, choose `core`, `ui`, `python` or `all`.
3. Approve the run in the `release` environment prompt. Watch the jobs; `github-release` creates the release
   (`core-v0.17.1`, ...) with the tarball/wheel and SBOM attached. For a `workflow_dispatch` run the tag is created by the
   release job at the commit that was released.

Workflow-dispatch runs refuse to run from any ref other than `refs/heads/main`.

## Verifying a release (for consumers)

**npm provenance and registry signatures**

```sh
npm install opentel-mcp        # in your project
npm audit signatures           # verifies registry signatures and provenance attestations of installed packages
```

The npm package page shows a "Provenance" section linking to the exact workflow run and commit for versions published
by this workflow. Versions published before this workflow existed (≤ `opentel-mcp` 0.18.0, ≤ `opentel-mcp-ui` 0.4.0) have no
provenance, so `npm audit signatures` reports registry signatures but no attestations for them; that is expected.
The first versions with provenance are `opentel-mcp` 0.18.1 and `opentel-mcp-ui` 0.4.1.

**PyPI attestations (PEP 740)** — per <https://docs.pypi.org/attestations/consuming-attestations/>:

```sh
pip install pypi-attestations
pypi-attestations verify pypi --repository https://github.com/Thirumalaiboobathi/opentel-mcp <direct URL of the wheel on files.pythonhosted.org>
```

This downloads the wheel and its provenance from PyPI's Integrity API, checks that the trusted publisher matches the
repository, and verifies the wheel against the attestation. Versions before the first workflow release (0.1.0) have none.

**GitHub artifact attestations** (tarball/wheel with SBOM predicate):

```sh
gh attestation verify opentel-mcp-<version>.tgz --repo Thirumalaiboobathi/opentel-mcp
```

## SBOMs

Each release attaches a CycloneDX JSON SBOM to its GitHub release (Releases page, asset list):

| Package | Asset | Generated with |
| --- | --- | --- |
| `opentel-mcp` | `opentel-mcp.cdx.json` | `npm sbom --sbom-format cyclonedx --omit dev` on the packed tarball ([`.github/scripts/npm-sbom.sh`](../../.github/scripts/npm-sbom.sh)) |
| `opentel-mcp-ui` | `opentel-mcp-ui.cdx.json` | same |
| `opentel-mcp` (PyPI) | `opentel-mcp-python.cdx.json` | `uv export --format cyclonedx1.5 --no-dev --frozen --preview` from `uv.lock` (a preview feature in uv) |

The npm SBOMs describe the package's production dependency tree as a consumer would install it (the consumer's own
MCP SDK, an optional peer, is not included). Each SBOM is also attached as a GitHub attestation to the tarball / wheel
(`actions/attest` with `sbom-path`); see the GitHub docs on `gh attestation verify` and its `--predicate-type` option
to check it (not yet verified by the maintainer against a real release). The Python SBOM lists locked runtime dependencies, which can be newer than what a consumer's resolver picks,
because the library declares ranges (`opentelemetry-api>=1.28`).

## Emergency manual publish (fallback)

Use only if the workflow is unavailable and a fix must ship. A manual `npm publish` **produces no provenance** (npm
only generates it inside a CI provider's OIDC context); it is how `opentel-mcp` 0.18.0 and `opentel-mcp-ui` 0.4.0
shipped. Follow every manual publish with a workflow release (a new patch version tagged `core-v…` / `ui-v…`) so the
latest version is attested again.

```sh
git switch --detach <tag-or-commit>
npm ci && npm test && npm run verify:tarball
npm login                                   # 2FA required
npm publish --workspace=packages/core       # or packages/ui  (prepublishOnly re-runs verify:tarball)
# Python
cd packages/python && uv build && uvx twine check dist/* && uvx twine upload dist/*   # needs a PyPI API token
```

Cost: that version has **no provenance and no PEP 740 attestation**, no SBOM attachment, no GitHub attestation. If you
disallowed token publishing on npm you must re-enable it temporarily (or publish with an interactive 2FA login if your
account policy allows). State in the GitHub release notes that the version was published manually, and create the
release/tag by hand. Prefer re-running the workflow later with a patch version over leaving an unattested version as
the latest.
